# An in-process C compiler, priced. ADR 0037's candidate table lists this row's per-definition
# cost and code quality as "unmeasured"; these are the readings.
#
# What was measured, and on what
# ------------------------------
# tcc, built from upstream (repo.or.cz/tinycc, mob) for arm64 Darwin. What Homebrew ships is
# 0.9.27, which predates Apple Silicon and is deprecated for removal on 2026-09-16; upstream has
# arm64-gen.c, arm64-link.c and tccmacho.c and configures for Darwin/arm64 without patching.
# It produces a loadable Mach-O dylib, so the C tier reaches it through `PLY_CC` and its existing
# dlopen path -- no libtcc binding was needed to read these numbers.
#
# It needs its own lib path (`-B<srcdir>`) to find libtcc1.a. Without it the compile succeeds and
# the dylib will not load, with an empty reason from dlerror.
#
# The emitted C needed one change to be readable at all: `__builtin_add_overflow` and its sibling
# were the only compiler builtins it required, and tcc has none of the overflow family.
# `ply_add_ov`/`ply_sub_ov` now stand in front of them.

## Compiling one unit
#
# The self-hosted front end's unit, as this tier emits it today: 1,511,374 lines, 96 MB.

compiler  wall     object

compiler  wall     object
tcc       0.021s   1.98 MB

## End to end, which is the number the loop would feel
#
# A cold `ply test --backend c` over the self-hosted front end -- 1153 definitions emitted,
# compiled, linked and loaded, nothing cached:
#
#   cc -O2    28.0s
#   tcc        3.1s
#
# The in-process tier this repository already has, Cranelift, compiles the same twelve modules in
# about 3.0s. So one code generator behind tcc reaches the other tier's compile time, which is the
# thing ADR 0037's table could not say without this row.

## The code it produces
#
# ADR 0035's two kernels through the C tier under each compiler, minimum of three, the two
# compilers counterbalanced by order. Load 3.43. The Rust bar is the same harness's.

arm       k1 ms    k2 ms    cold build
rust      0.071    8.00     --
cc -O2    0.174    31.3     1.62s
tcc       2.105    48.6     0.42s

# Against the bar: cc -O2 is 2.4x on k1 and 3.9x on k2; tcc is 29.6x and 6.1x.
#
# The two kernels answer differently and the reason is where their time is. k1 is integer work in
# registers, which is what an optimising compiler is for -- tcc is 12x worse. k2 spends most of
# itself inside runtime helpers that are already-optimised Rust, so the compiler that emitted the
# calls matters much less -- 1.55x. A tier that leans on the runtime is cheap to compile badly.

## What it gets wrong, and what that turned out to be
#
# At the inlining depth this tier used when these were first read -- six -- three of `examples/`'s
# files segfaulted under tcc and ran under `cc` (agreement, desk, twin_divergence_audit). Both
# compilers linked the same unit and exported the same symbols, so it was code generation rather
# than linking, and the natural reading was "tcc's arm64 backend is not to be trusted".
#
# It was a function-size effect, and it is not tcc's: `cc -O0` and `cc -O1` do it too. Depth is
# the setting that answers it. At depth *zero* everything runs under every one of them:
#
#   examples/            186 passed, 0 failed, audited against the machine
#   the front end        156 passed, 0 failed, audited against the machine
#
# Depth three was enough when this file was written and is not now -- the corpus grew deeper as
# this tier's coverage grew, because a definition this tier takes is a native frame where it used
# to be an interpreter one. `observation-loop-profile.txt` has the frame sizes and the mechanism,
# and `PLY_C_PROFILE=loop` is the setting that carries the compiler and the depth together, so
# that nobody has to know this to use a fast compiler.
#
# (A fourth file, report.ply, does not compile *standalone* under either compiler: it imports a
# sibling module. It was never a tcc failure; the sweep that found it was reading the absence of
# a summary line as a crash.)
#
# So the row this file exists to fill reads: an in-process C compiler runs this tier's whole
# corpus correctly, at a twelfth of the integer kernel's speed and a 790th of the compile -- with
# the inlining turned off, which costs most of the rest of that twelfth.
