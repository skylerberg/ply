# The Ply arm now measures the kernel rather than the run.
#
# Readings in this directory taken before this change are not comparable to ones taken after it.
# That is the change, not a side effect of it.
#
# What was wrong
# --------------
# `benches/value-model/rust` takes the minimum over twenty calls **inside one process**. The Ply
# arm ran each kernel *once* per process and took the minimum over three processes, so it carried
# a whole run's fixed cost -- process start, page cache, whatever the allocator was holding --
# where the Rust arm carried none of it. k1 is a fifth of a millisecond. The fixed cost is of that
# order.
#
# It showed as a verdict that moved. Six arms in one day, both tiers, counterbalanced, all at load
# 3.2-3.5, put the C tier's k1 ratio at 2.20, 2.46, 2.76, 2.97, 3.41 and 3.69 against a bar of
# 3.0 -- "within" three times, "undecided" twice, "OVER" once. That is a spread of 1.5 ratio
# points on an unchanged binary.
#
# The seam was not the problem. `ply test --audit-backend` reports k1 as `entered 1, declined 0`:
# one call into compiled code and never back out, the hash entirely compiled. What was being timed
# around that one call was the rest of `ply test`.
#
# What it is now
# --------------
# `ply-arm/` builds the fragment once, then calls the kernel's entry directly and takes the
# minimum, in one process, exactly as the Rust arm does. Five invocations of each, interleaved:
#
#   repeats        C tier k1 ratios              spread
#   1 (old)        2.20 2.46 2.76 2.97 3.41 3.69   1.50
#   20             2.79 2.37 2.49 2.60 2.96        0.59
#   200            2.60 2.61 2.73 2.79 2.80        0.20
#
#   200            cranelift  4.74 4.57 4.63 4.44 4.61   spread 0.30
#
# k1 gets two hundred repeats and k2 twenty, because k2 is two hundred times the longer and
# already settles: its minima span 29.70 to 30.04 across five invocations, a little over one
# percent.
#
# All three arms assert the same digest, so an arm that drifts fails rather than skews.
#
# What it says
# ------------
# Against the bar of 3.0, with the resolution now 0.20 rather than 1.5:
#
#   kernel   C tier   cranelift   rust
#   k1       2.6-2.8  4.4-4.7     0.070ms
#   k2       3.7      1.7         7.97ms
#
# Each tier clears the bar on one kernel and misses on the other, and both statements are now
# outside the noise. The C tier's k1 is the first arrangement in this repository to clear it.
#
# Through the gate itself
# ----------------------
# `run.sh` with the new arm, both tiers, counterbalanced by order, load 3.3-3.9:
#
#   arm         k1                        k2
#   c           2.56 within               3.80 OVER
#   cranelift   4.54 OVER                 1.71 within
#   cranelift   4.48 OVER                 1.69 within
#   c           2.56 within               3.52 OVER
#
# The C tier's k1 is 2.56 in both orders, to two decimal places. Under the old arm the same
# question got 2.20, 2.46, 2.76, 2.97, 3.41 and 3.69.
#
# On the control, and a correction
# -------------------------------
# `analyze.py` reports `resolution = |ply - null| / rust`, and `null` is the same command as `ply`
# under a different label -- so that distance is a noise estimate, which is what an error bar is.
# An earlier note in this directory called it a measure of signal rather than of error and was
# wrong about it.
#
# What was true is that it estimated the wrong noise. `ply` and `null` were two runs inside one
# interleaved series, minutes apart and sharing warm state, so the control saw what varied within
# a series and nothing of what varied between them:
#
#   arm         ply        null       rust       resolution   ratio
#   c           0.000242   0.000214   0.000071   0.39         3.41
#   c           0.000211   0.000201   0.000071   0.14         2.97
#   cranelift   0.000358   0.000367   0.000071   0.13         5.04
#
# 0.13 to 0.39 of a ratio point within a series, against 1.5 between them. With each reading now a
# minimum over two hundred calls, the two agree.

# What it does not measure
# ------------------------
# The command a user runs. `ply test` compiles the unit, installs a backend, runs a test runner
# and prints a report, and none of that is here. That is right for a gate about the value model's
# speed and wrong for a question about what a run costs, which `benches/marginal-change/` and
# `benches/c-floor/` are for.
