# k1's verdict swings between runs by far more than the control admits.
#
# Six arms over one day, both tiers, counterbalanced, every one at load 3.2-3.5. The C tier's k1
# ratio against a bar of 3.0:
#
#   2.20 within · 2.46 within · 2.76 within · 2.97 undecided · 3.41 OVER · 3.69 undecided
#
# The in-process tier's, for contrast, was 5.04, 5.21, 5.27, 5.35 -- a spread of 0.3 where the C
# tier's is 1.5.
#
# What the control does and does not cover
# ----------------------------------------
# `null` is the same command as `ply` under a different label (PRE-REGISTERED.md, "Arms"), so
# `resolution = |ply - null| / rust` is a noise estimate and a legitimate error bar. It is not,
# as an earlier draft of this file claimed, a measure of signal that shrinks as the kernel gets
# faster; that reading was wrong and the numbers below are what corrected it.
#
# The trouble is which noise it estimates. `ply` and `null` are two runs inside one interleaved
# series, minutes apart, so the control sees what varies within a series and nothing of what
# varies between them:
#
#   arm         ply        null       rust       resolution   ratio
#   c           0.000242   0.000214   0.000071   0.39         3.41
#   c           0.000211   0.000201   0.000071   0.14         2.97
#   cranelift   0.000358   0.000367   0.000071   0.13         5.04
#   cranelift   0.000370   0.000369   0.000071   0.01         5.21
#
# Within a series the measurement repeats to within 0.01-0.39 of a ratio point. Repeat the whole
# series and the C tier's ratio moves by 1.5. The error bar understates the uncertainty by an
# order of magnitude, and it is the between-series number a verdict should be read against.
#
# Why k1 and not k2
# -----------------
# k1 hashes 64KB in about a fifth of a millisecond. A run's fixed cost -- process start, the
# backend's own warm-up, whatever the page cache is holding -- is of that order, constant inside a
# series and not between them. `floor` is measured for exactly this and is subtracted from
# nothing, by design ("the floor is subtracted from neither"). k2 runs for 30ms and does not have
# the problem: its ratios are 3.68, 3.73, 3.76, 3.93 across the same six arms.
#
# What would fix it, neither of which is free
# -------------------------------------------
# 1. Grow k1's input until the kernel dominates the run's fixed cost. An order of magnitude puts
#    it at about 2ms. Every prior reading in this directory then means something different, which
#    is why this is a decision and not a patch.
# 2. Report the statistic over repeated *series* rather than over blocks within one, so the
#    resolution is the spread a reader would actually get by running it again.
#
# Until one of them, k1's verdict is not evidence either way, and this file is here so that a
# reading of 2.46 is not quoted as a pass. What the six arms do support, because it is a repeated
# difference between two arms measured the same way, is that the C tier's k1 path is about half
# the in-process tier's: 0.000211-0.000242 against 0.000358-0.000387.
